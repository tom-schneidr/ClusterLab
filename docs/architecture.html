ClusterLab Architecture

ClusterLab is a local-first FastAPI application with a static browser client, SQLite persistence, and an OpenAI-compatible LLM provider boundary.

Runtime Shape

  • app.py exposes the ASGI application for Uvicorn.
  • clusterlab/config.py centralizes environment parsing and runtime defaults.
  • clusterlab/app_factory.py constructs the FastAPI app, static file mount, database store, and API router.
  • clusterlab/api/ owns HTTP routes, request schemas, response models, and consistent error payloads.
  • clusterlab/engine.py owns run orchestration and blackboard updates.
  • clusterlab/blackboard.py owns blackboard shape, compaction, update routing, and deltas.
  • clusterlab/topology.py owns graph role lookup, edge traversal, and topology validation.
  • clusterlab/storage.py migrates and persists hats, topologies, runs, and run events in SQLite.
  • clusterlab/llm.py calls an OpenAI-compatible /chat/completions endpoint.

Frontend Shape

The frontend intentionally stays build-free while the project is small. static/app.js contains UI behavior, while shared primitives live in static/js/.

static/js/api.js        API helper
static/js/config.js     browser UI copy and small presentation constants
static/js/constants.js  graph constants, tool IDs, palette templates
static/js/dom.js        DOM and formatting helpers
static/js/graph/        canvas rendering, pan/zoom, ports, layout, execution feedback
static/js/selectors.js  state-derived lookup and display helpers
static/js/state.js      shared mutable UI state

Storage Lifecycle

SQLite schema changes are applied through the schema_migrations table. Seed hats and the default topology are written idempotently after migrations. Runtime databases live under data/ by default and are intentionally ignored by Git.

Run Lifecycle

  1. The UI saves or selects a topology.
  2. POST /api/runs/start creates a queued run and starts a background worker thread.
  3. The worker marks the run running, then loads the topology and hats from SQLite.
  4. The engine validates the topology and builds a stage plan.
  5. Each hat receives a prompt built from the task, stage, typed edges, upstream outputs, and compact blackboard.
  6. Outputs are appended as run events and selectively written back to the blackboard.
  7. The final result is persisted with status completed, failed, or stopped, and polling returns the event trace.

Growth Rules

  • Keep route handlers thin; move business logic into domain modules.
  • Keep config reads behind clusterlab/config.py.
  • Add tests at API, storage, topology, and engine boundaries before large behavior changes.
  • Keep SQLite until multi-user or remote deployment requirements are concrete.
  • Keep vanilla JavaScript until UI complexity justifies a build step.
  • Prefer explicit migrations before changing persisted schema.
